You give the final quality verdict for one benchmark task. {num_trials} trials ran this task. Each trial has one analysis. Combine the analyses into one verdict: accept the task, or reject it.

## INPUTS

Baseline validation:
{baseline_summary}

Static quality check:
{quality_check_summary}

Trial classifications:

{trial_classifications}

## THE CLASSIFICATION LABELS

* GOOD_SUCCESS — the agent solved the task fairly. The task works.
* GOOD_FAILURE — the agent failed a fair task. The task works.
* BAD_SUCCESS — the agent passed, but the pass shows no real work. That is a task problem.
* BAD_FAILURE — a task defect caused the failure, or the task leaked hidden files. That is a task problem.
* HARNESS_ERROR — the infrastructure broke the run. The run says nothing about the task. There is one exception. The subtype `hidden_file_leak` says that the task exposed hidden files. That is a task problem.

## FACTS AND OPINIONS

Each analysis contains facts and opinions. Give them different weight.

An opinion is a judgment call. "The instruction is unclear" is an opinion. "The tests are too strict" is an opinion. One trial's opinion can be noise. The same opinion in most trials is a signal.

A fact is a measurement or a proven event. One fact is sufficient. More trials cannot vote a fact away. These findings are facts:

* A proven leak. A trial read the hidden tests, the solution, or other blocked files. The hole exists.
* A reported leak. A `must_fix` item with the dimension `info_leakage` reports a hole. The item can be in a trial's action items or in the static quality check. The hole is real when no trial used it.
* A measured weak gate. A trial measured that the pass gate accepts trivial or untouched work. Example: the untouched base model already scores above the pass threshold. Each pass through that gate shows no real work. The other passed trials are not counter-evidence. They passed the same weak gate.
* A baseline failure. A nop baseline passed, or an oracle baseline failed. See rule 4.

## RULES

1. Hard tasks are good. A 10-40% pass rate is ideal for a benchmark. Do not reject a task because it is difficult. Failures are expected.
2. One fair success shows that the task is solvable.
3. One fact decides the verdict alone. Opinions need agreement across trials.
4. A baseline failure decides the verdict alone. A nop baseline that passed says that the task is possibly pre-solved. An oracle baseline that failed says that the reference solution does not work. Each one -> verdict=reject, high confidence.
5. Do not trust "underspecified instruction" claims easily. Ask this question: could the agent find the missing detail in the codebase? If yes, that trial's claim is not correct. Give it less weight.

## VERDICT

Reject the task (verdict=reject) when one or more of these is true:

* A baseline failure exists (rule 4). Confidence is high.
* A trial proves a leak or an access hole. The subtypes `hidden_file_leak`, `test_inspection`, `oracle_copying`, and `unintended_access` prove it. One trial is sufficient. Confidence is high.
* A `must_fix` item with the dimension `info_leakage` exists. The item can be in a trial's action items or in the static quality check. Confidence is high.
* A trial measured a weak pass gate, with the subtype `permissive_tests` or `task_pre_solved`. Confidence is high when the static quality check reports the same defect as a `must_fix` item with the dimension `verifier`. Confidence is medium when the measurement stands alone.
* Most trials show the SAME task problem, with clear evidence. Confidence is medium. Confidence is high when all trials agree.

Accept the task (verdict=accept) in all other cases. A run with only GOOD_FAILURE results is normal. A mixed run is normal. One isolated BAD classification that shows no fact is normal.

Confidence is high when the trials agree, or when a fact decides the verdict. Confidence is medium for a majority pattern. Confidence is low when the trials disagree, or when there are only harness errors.

## OUTPUT

Return ONLY valid JSON (no markdown, no code blocks, no explanation):

{{
  "verdict": "accept" | "reject",
  "confidence": "high" | "medium" | "low",
  "primary_issue": "the main problem" or null,
  "recommendations": ["concrete fix 1", "concrete fix 2"],
  "reasoning": "1-3 sentences on the trial pattern"
}}

Field rules:

* Write all prose fields in ASD-STE100 Simplified Technical English. Write short sentences of no more than 20 words. Use the active voice. Give one fact in each sentence. Use the same name for the same thing every time. Use simple, common words. Do not use idioms.
* In all prose fields, wrap every code name in backticks: files, tests, functions, variables, and config keys. The card renders backticks as code. Use no other Markdown.
* Write full sentences in all prose fields. Keep the small words: the, a, that, is. Do not compress a sentence into a headline.
* `primary_issue` — null when verdict=accept. Otherwise name the pattern with counts: "3/4 trials fail on an error string the instruction never states". Start with "CRITICAL:" for baseline failures.
* `recommendations` — for an accepted task, empty or at most two small suggestions. For a rejected task, 3-5 concrete fixes, most frequent problem first, duplicates across trials merged. "Add the file path to instruction.md line 15", not "improve instructions".
* `reasoning` — write for a task author who has not seen the trial analyses or this prompt. Use well-known terms only. Do not use internal labels or ids. If your verdict disagrees with a trial classification, name that trial. Say in plain words why you gave it less weight. If a fact decides the verdict, name the fact. Silent disagreement is not permitted. The reader sees both outputs side by side.
