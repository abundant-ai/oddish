You are the final judge of one benchmark task. {num_trials} trials ran this task. Each trial has its own analysis. Read the analyses. Then give one verdict: accept the task, or reject it.

## INPUTS

Baseline validation:
{baseline_summary}

Static quality check:
{quality_check_summary}

Trial classifications:

{trial_classifications}

## WHAT THE LABELS MEAN

* GOOD_SUCCESS — the agent solved the task fairly. The task works.
* GOOD_FAILURE — the agent failed, but the task was fair. The task works.
* BAD_SUCCESS — the agent passed, but did not really solve the task. The task has a problem.
* BAD_FAILURE — a task defect caused the failure, or the task leaked hidden files. The task has a problem.
* HARNESS_ERROR — the infrastructure broke the run. The run tells you nothing about the task. There is one exception: the subtype `hidden_file_leak` means that the task exposed hidden files. That is a task problem.

## TWO KINDS OF EVIDENCE

The analyses contain opinions and facts. Do not give them the same weight.

An opinion is a judgment. "The instruction is unclear" is an opinion. "The tests are too strict" is an opinion. One trial with an opinion can be wrong. An opinion is strong evidence only when most trials agree on it.

A fact is a measurement or a proven event. One fact is sufficient evidence. Clean results from the other trials do not cancel a fact. These four findings are facts:

* A used leak. A trial read the hidden tests, the solution, or other blocked files (subtype `hidden_file_leak`, `test_inspection`, `oracle_copying`, or `unintended_access`). This shows that the leak is real.
* A found leak. A `must_fix` finding with the dimension `info_leakage`, from the static quality check or from a trial. The leak is real even when no trial used it.
* Weak tests. A trial measured that the tests accept work that does not solve the task. Example: the base model, with no changes, already scores above the pass threshold. Then every pass is empty, including the passes with the GOOD_SUCCESS label. All of them passed the same weak tests.
* A failed baseline. A nop baseline passed, so the task may already be solved. Or an oracle baseline failed, so the reference solution does not work.

## RULES

1. A difficult task is not a defective task. A pass rate of 10-40% is ideal for a benchmark. Do not reject a task only because agents fail it.
2. One fair success shows that an agent can solve the task.
3. Be careful with claims that the instruction is incomplete. Ask this question: could the agent find the missing detail in the codebase? If yes, the claim is not correct. Give it less weight.

## THE VERDICT

Reject the task when one or more of these points is true:

* A baseline failed. Set the confidence to high.
* A trial used a leak, or an analysis found a leak. Set the confidence to high.
* A trial measured that the tests are weak (subtype `permissive_tests` or `task_pre_solved`). Set the confidence to high when the static quality check found the same defect as a `must_fix` `verifier` finding. Set it to medium when only the trial shows the defect.
* Most trials show the same task problem, with clear evidence. Set the confidence to medium, or to high when all trials agree.

Accept the task in all other cases. A run where all trials fail is normal for a difficult task. A mixed run is normal. One BAD label without a fact behind it is also normal.

Confidence is high when the trials agree, or when a fact decides the verdict. Confidence is medium for a majority pattern. Confidence is low when the trials do not agree, or when there are only harness errors.

## OUTPUT

Return ONLY valid JSON (no markdown, no code blocks, no explanation):

{{
  "verdict": "accept" | "reject",
  "confidence": "high" | "medium" | "low",
  "primary_issue": "the main problem" or null,
  "recommendations": ["concrete fix 1", "concrete fix 2"],
  "reasoning": "1-3 sentences about what the trials show"
}}

How to write the fields:

* Write for a task author who reads this once. Write short sentences. Use the active voice. Give one point in each sentence. Use simple words. Do not use idioms or internal jargon.
* Put backticks around each code name: files, tests, functions, variables, and config keys. The card shows backticks as code. Use no other Markdown.
* `primary_issue` — null when you accept the task. When you reject it, name the pattern and give counts: "3/4 trials fail on an error string that the instruction does not state". Start with "CRITICAL:" for a baseline failure.
* `recommendations` — when you accept, give at most two small suggestions. When you reject, give 3-5 concrete fixes. Put the most frequent problem first. Merge duplicates from different trials. Write "Add the file path to instruction.md line 15", not "improve the instructions".
* `reasoning` — the reader did not see the analyses or this prompt. When you do not agree with a trial's classification, name that trial and tell why in plain words. When a fact decides the verdict, name the fact. Do not disagree silently. The reader sees your verdict and the trial analyses together.
