## THE LABELS

* GOOD_SUCCESS — the agent solved the task fairly. The task is good.
* GOOD_FAILURE — the agent failed a fair task. The task is good.
* BAD_SUCCESS — the agent passed without solving the task. The task has a problem.
* BAD_FAILURE — a task problem caused the failure, or the task leaked hidden files. The task has a problem.
* HARNESS_ERROR — the infrastructure broke the run, so it gives no data about the task. Exception: the subtype `hidden_file_leak` means the task exposed hidden files, and that is a task problem.

## IMMEDIATE REJECTION

Look for this evidence first. If you find one item, reject the task. The other trials do not change this.

* A used leak. A trial read the hidden tests, the solution, or other closed files (subtype `hidden_file_leak`, `test_inspection`, `oracle_copying`, or `unintended_access`).
* A found leak. A `must_fix` finding with the dimension `info_leakage`, from the static quality check or from a trial. It counts even if no trial used the leak.
* Weak tests. A trial measured that work that does not solve the task still passes. Example: the untouched base model already scores above the pass threshold. Then no pass on this task is evidence, not even a GOOD_SUCCESS.
* A failed baseline. A nop baseline makes no changes; if it passed, the task may already be solved. An oracle baseline applies the reference solution; if it failed, that solution is broken.

## JUDGMENT

Everything else is opinion: "the instruction is unclear", "the tests are too strict". One trial's opinion can be wrong. Use an opinion only when most trials agree.

1. A difficult task is not a bad task. A benchmark is best when 10-40% of trials pass. Do not reject a task because agents fail it.
2. One fair success shows the task is solvable.
3. For a claim about missing information, ask: could the agent find it in the code? If yes, ignore the claim.

Reject when most trials show the same task problem, with clear evidence. Accept everything else. A run where all trials fail is normal. A mixed run is normal. One BAD label alone is normal.

## CONFIDENCE

* If you reject the task immediately, set the confidence to high. There is one exception: if the only evidence is one trial that showed weak tests, with no matching `must_fix` `verifier` finding, set it to medium.
* If you reject because most trials show the same problem, with clear evidence, set the confidence to high.
* If you accept and the trials agree, set the confidence to high. If the trials disagree, or if all trials are harness errors, set it to low.

## OUTPUT

Return ONLY valid JSON (no markdown, no code blocks, no explanation):

{{
  "verdict": "accept" | "reject",
  "confidence": "high" | "medium" | "low",
  "primary_issue": "the main problem" or null,
  "recommendations": ["concrete fix 1", "concrete fix 2"],
  "reasoning": "1-3 sentences about what the trials show"
}}

Field rules:

* Write for a task author. Write short sentences in the active voice. Give one fact per sentence. Use simple words, never idioms.
* Wrap every code name in backticks: files, tests, functions, variables, config keys. Use no other Markdown.
* `primary_issue` — null when you accept. Otherwise give the problem and the trial count: "3/4 trials fail on an error string that the instruction does not give". Start with "CRITICAL:" for a failed baseline.
* `recommendations` — at most two suggestions when you accept. When you reject, 3-5 exact fixes, most frequent problem first, each fix written once. Write "Add the file path to instruction.md line 15", not "improve the instructions".
* `reasoning` — the reader has not seen the analyses. If you reject immediately, name the evidence. If you disagree with a trial's classification, name the trial and the reason.
