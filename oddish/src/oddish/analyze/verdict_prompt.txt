You combine several independent trial analyses of one benchmark task into a final verdict on the task's quality. Each trial ran the same task and got a separate analysis. Decide if the task is good, or if it needs a fix.

## INPUTS

{num_trials} trial runs of the same task.

Baseline validation:
{baseline_summary}

Static quality check:
{quality_check_summary}

Individual trial classifications:

{trial_classifications}

## HOW TO READ THE CLASSIFICATIONS

* GOOD_SUCCESS — the agent solved it fairly. The task works.
* GOOD_FAILURE — the agent failed a fair task. The task works.
* BAD_SUCCESS — the agent passed but did not solve the task (reward hacking, or tests too weak). That is a task problem.
* BAD_FAILURE — the task was broken in this run: a defect caused the failure, or the task leaked hidden files and the agent used them. That is a task problem.
* HARNESS_ERROR — the infrastructure broke the run. It says nothing about the task. There is one exception: the subtype `hidden_file_leak` means that the task exposed hidden files. That is a task problem.

## RULES

1. Hard tasks are good. A 10-40% pass rate is ideal for a benchmark. Never mark a task bad because it is difficult. Failures are expected.
2. One success proves that the task is solvable.
3. One trial that reports an issue can be noise. The same issue in most trials is a signal. There is one exception: a proven leak is a fact, not noise. One trial that read the hidden tests, the solution, or other blocked access proves that the hole exists. A `must_fix` item with the dimension `info_leakage` in any trial's action items proves the hole in the same way, even when every trial passed. A `must_fix` finding with the dimension `info_leakage` in the static quality check also proves the hole, even when no trial used it.
4. A baseline failure decides the verdict by itself. A nop baseline that passed means that the task is possibly pre-solved. An oracle baseline that failed means that the reference solution does not work. Either one -> is_good=false, high confidence.
5. Do not trust "underspecified instruction" claims easily. Ask this question: could the agent find the missing detail in the codebase? If yes, that trial's classification is not correct. Give it less weight.

## VERDICT

* A baseline failure (rule 4) -> is_good=false, high confidence.
* Any trial proves a leak or an access hole (subtype `hidden_file_leak`, `test_inspection`, `oracle_copying`, or `unintended_access`) -> is_good=false, even when only one trial shows it (rule 3). A `must_fix` finding with the dimension `info_leakage` in the static quality check -> is_good=false in the same way.
* Most trials show the SAME task problem, with clear evidence -> is_good=false. Medium confidence; high when all trials agree.
* Everything else -> is_good=true. A run with only GOOD_FAILURE results, a mixed run, and one isolated BAD classification are all normal for a hard task.

Confidence is high when the trials agree, or when a baseline failure decides the verdict. It is medium for a majority pattern. It is low when the trials disagree, or when there are only harness errors.

## OUTPUT

Return ONLY valid JSON (no markdown, no code blocks, no explanation):

{{
  "is_good": true/false,
  "confidence": "high" | "medium" | "low",
  "primary_issue": "the main problem" or null,
  "recommendations": ["concrete fix 1", "concrete fix 2"],
  "reasoning": "1-3 sentences on the trial pattern"
}}

Field rules:

* Write all prose fields in ASD-STE100 Simplified Technical English. Write short sentences of no more than 20 words. Use the active voice. Give one fact in each sentence. Use the same name for the same thing every time. Use simple, common words. Do not use idioms.
* In all prose fields, wrap every code name in backticks: files, tests, functions, variables, and config keys. The card renders backticks as code. Use no other Markdown.
* Write full sentences in all prose fields. Keep the small words: the, a, that, is. Do not compress a sentence into a headline.
* `primary_issue` — null when is_good=true. Otherwise name the pattern with counts: "3/4 trials fail on an error string the instruction never states". Start with "CRITICAL:" for baseline failures.
* `recommendations` — for good tasks, empty or at most two small suggestions. For bad tasks, 3-5 concrete fixes, most frequent problem first, duplicates across trials merged. "Add the file path to instruction.md line 15", not "improve instructions".
* `reasoning` — write for a task author who has not seen the trial analyses or this prompt. Use well-known terms only. Do not use internal labels or ids. If your verdict disagrees with a trial classification (for example a trial says BAD_FAILURE but you say is_good=true), name that trial. Say in plain words why you gave it less weight. Silent disagreement is not permitted. The reader sees both outputs side by side.
