# Oddish Pull Artifact Layout

Use this reference when explaining or inspecting a local `oddish pull` output directory.

## Root Files

- `manifest.json`: pull-run manifest written by the CLI. It records target type/id, pull time, task summaries, trial summaries, and pull errors when the CLI completes normally.
- `analysis-summary.md`: optional human summary generated by `scripts/summarize_pull.py`.
- `analysis-summary.json`: optional machine-readable summary generated by `scripts/summarize_pull.py`.

## Task Files

`tasks/<task-id>/task.json` is the primary task payload. Important fields:

- `id`, `name`, `status`, `progress`, `created_at`, `started_at`, `finished_at`
- `experiment_id`, `experiment_name`, `experiment_is_public`
- `github_username`, `github_meta`, `user`
- `total`, `completed`, `failed`, `reward_success`, `reward_sum`, `reward_total`
- `run_analysis`, `verdict_status`, `verdict`, `verdict_error`
- `trials[]`: per-trial metadata and analysis

`tasks/<task-id>/files/` contains original task source files downloaded with `--include-task-files`, typically `instruction.md`, `task.toml`, and task-specific source/config files.

## Trial Files

Each trial lives under `trials/<trial-id>/`.

Top-level trial files:

- `logs.txt`: raw trial log text from Oddish/Harbor.
- `logs_structured.json`: parsed logs with buckets such as `agent`, `verifier`, `exception`, and `other`. This is structured logging, not LLM analysis.
- `result.json`: terminal result/stats payload for completed trials.
- `trajectory.json`: agent trajectory when available; usually contains `schema_version`, `session_id`, `agent`, `steps`, and `final_metrics`.
- `config.json`: trial/run configuration captured from the Harbor run.
- `job.log`: worker/job log from the downloaded trial artifacts.
- `modal-output.log`: Modal execution output when available.

Downloaded Harbor workspace:

- `trials/<trial-id>/task-.../trial.log`: Harbor trial log.
- `trials/<trial-id>/task-.../result.json`: Harbor-side result payload.
- `trials/<trial-id>/task-.../config.json`: Harbor-side config.
- `trials/<trial-id>/task-.../agent/`: agent-side files, transcripts, temp files, or model-specific outputs.
- `trials/<trial-id>/task-.../verifier/`: verifier outputs such as `test-stdout.txt`, `reward.txt`, and `reward.json`.
- `trials/<trial-id>/task-.../artifacts/`: task-declared artifacts and an `artifacts/manifest.json` when present.

## Analysis Fields

Oddish LLM analysis is stored inside `tasks/<task-id>/task.json` on each `trials[]` entry:

- `analysis_status`: analysis lifecycle state, such as `queued`, `running`, `success`, or error states.
- `analysis.classification`: common values include `GOOD_SUCCESS`, `GOOD_FAILURE`, `BAD_FAILURE`, `BAD_SUCCESS`, and `HARNESS_ERROR`.
- `analysis.subtype`, `analysis.evidence`, `analysis.root_cause`, `analysis.recommendation`: explanatory fields.

Task-level verdicts, when computed, live in `verdict_status`, `verdict`, and `verdict_error` on the task object.

## Completeness Checks

- Running trials may have `logs.txt` and `logs_structured.json` but no final `result.json`, trajectory, or completed analysis.
- Completed trials can still have `analysis_status: queued` or `running`; pull again later if the user needs final LLM classifications.
- `_pull_errors/**/*.error.txt` means some artifact file failed to download. Retry those individual files or rerun `oddish pull`; the CLI skips existing files by size.
