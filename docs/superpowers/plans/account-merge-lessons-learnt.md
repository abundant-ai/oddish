## Traps already hit (don't repeat)
- **Mapper config fails without the conftest FK shim.** `OrganizationModel.api_keys` / `UserModel.api_keys` relate to `api_keys`, whose `org_id`/`created_by_user_id` have NO model-level FK (OSS omits them; cloud adds via migration `a1b2c3d4e5f6`). `configure_mappers()` then raises `NoForeignKeysError` and every backend DB test errors. `backend/tests/conftest.py` appends those FKs (with prod `ondelete`: org_id→CASCADE, created_by_user_id→SET NULL) at import. Leave that shim in place.
- **No backend pytest job in CI.** Only migration/preview workflows touch a DB. So these tests run only locally — don't assume CI catches a DB-test break.
- **xfail(strict) etiquette.** When your slice makes an xfail test pass, you MUST remove the `@pytest.mark.xfail(...)` line, or strict mode turns the unexpected pass into an XPASS failure.
- **Fail-open must catch broadly.** `fetch_github_identity_from_clerk` does `response.json()` *inside* its `except httpx.HTTPError` guard, so a malformed-200 / JSONDecodeError escapes it. Any best-effort Clerk path must `except Exception` (log + continue), not just `httpx.HTTPError`, or it 500s instead of degrading.
- **get_session() auto-commits on clean exit** (`oddish/db/connection.py`) and autoflush makes an in-session re-`select` see pending writes — no explicit commit needed inside the `async with`.
- **The Clerk fetch now returns a dataclass, not a tuple (G3).** `fetch_github_identity_from_clerk` / `_github_account_from_clerk_payload` return `ClerkGithubIdentity(username, email, github_id)`. Any new caller must use attribute access (`identity.username`), NOT `a, b = await …` positional unpack — the old 2-tuple form is gone. All existing call sites were migrated in G3.
- **A github_id collision pre-check must span ALL org rows — drop `is_active` AND lift the soft-delete filter.** `uq_users_org_github_id` covers every physical row (active, inactive, AND soft-deleted). `UserModel` is soft-delete-registered (`register_soft_delete_models`, backend/models.py), so an ordinary ORM `select(UserModel)` auto-appends `deleted_at IS NULL` and hides tombstoned holders → the pre-check passes and then IntegrityErrors at commit. Fix: `.execution_options(include_deleted=True)` (see `oddish/db/soft_delete.py`) AND no `is_active` filter. `_set_github_id_if_absent` does both (Codex caught the soft-delete miss on G3). Residual TOCTOU (concurrent same-github_id provisioning) is accepted — near-impossible, robust reject deferred to plan Q19. G5's backfill pre-check must use include_deleted too.
- **Don't add a Clerk GET to the auth hot path to backfill github_id.** `_refresh_user_github_identity` runs on every login via `get_or_create_user_in_org`. Its early-return must stay keyed on `github_username` only — gating it on github_id too makes every un-backfilled user hit Clerk on every login (a storm on the latency-sensitive auth path). github_id is captured *opportunistically* only when Clerk is already fetched (new / handle-less users); existing handle-having users get it from G5's batch backfill, NOT the hot path. (G3 initially relaxed this; corrected in review.)
- **Adding a field to `TaskSweepSubmission` perturbs the server idempotency hash.** `compute_request_hash` (`oddish/core/idempotency.py`) dumps the full model, so a new optional field appears as `null` for everyone and changes the hash — an in-flight `Idempotency-Key` retried across the deploy boundary then spuriously 409s. Fix is surgical: drop the new field from the dump when unset (NOT `exclude_none`/`exclude_unset`, which perturb *every* submission's hash). Caught by Codex on G2; any future slice adding a hashed field must do the same.
- **Backfills are imported callables invoked from the reconciler — NOT standalone `python -m` scripts.** `dashboard_owner_backfill.backfill_experiment_owners` is called best-effort (try/except phase) from the Modal-scheduled `worker/functions.py::reconcile_queue_state`; there is no `__main__`. Follow that exactly. Why it matters: a truly standalone `python -m <backend module>` run hits `NoForeignKeysError` at the first User/Org query — the OSS schema omits model-level `api_keys` FKs (cloud adds them via migration `a1b2c3d4e5f6`), so mapper config of `*.api_keys` fails outside the app bootstrap AND outside the conftest shim. The reconciler-import path configures mappers via the worker app graph, so no shim is needed. (G5 originally added a `main()`-only FK shim for a standalone entry; dropped in review in favour of wiring `backfill_github_id(max_users=200)` into the reconciler like the owner backfill.)
- **PRE-EXISTING failure (NOT G4): `tests/test_sweep_idempotency.py::test_migration_applies_and_downgrades_cleanly`.** It does `stamp(head)` → `downgrade -1` and asserts the `submission_idempotency` table is gone. But G1's `g1h2i3j4k5l6` (down_revision `s5t6u7v8w9x0`, the idempotency migration) is now the head, so `downgrade -1` runs *G1's* downgrade (drops `users.github_id`) and leaves `submission_idempotency` in place → assertion fails. This broke when **G1 stacked its migration on top of the idempotency migration**, not from any G4 code (G4 touches no migrations). The test then `upgrade head`s, so it self-heals the DB (github_id + idempotency table both present afterward — verified). Whoever owns the migration chain should re-point this test at the idempotency revision explicitly rather than `-1`. It also churns the shared test DB (drops/recreates `public`), so run it separately from the gate suite.

- **Never share one AsyncSession across `asyncio.gather`ed coroutines.** SQLAlchemy AsyncSession is not safe for concurrent operations — two gathered coroutines both awaiting `session.execute(...)` corrupt/raise. Pattern for a throttled batch (G5): run the slow I/O (Clerk GETs) concurrently under a `Semaphore`, collect `(item, result, error)`, THEN apply the DB writes SEQUENTIALLY on the shared batch session. (Codex caught the shared-session gather on G5; a tiny-N test masked it.)
- **The backfill has NO in-run retry — and that's deliberate.** `fetch_github_identity_from_clerk` swallows `httpx.HTTPError` into an empty identity, so a retry loop around it never sees transient errors (they'd be miscounted as skipped anyway). Instead the reconciler's periodicity IS the retry: a Clerk-unreachable user stays `github_id IS NULL` and is re-attempted next cycle. Don't re-add a retry loop expecting it to catch HTTP failures unless you also stop swallowing them.

## Design invariants to preserve
- **Predicate parity (INV2):** "connected?" (endpoint) == "resolvable owner?" (`/tasks/sweep`). Both go through the SAME resolver in `api/routers/tasks.py`. **As of G4 that resolver is `_resolve_connected_user(session, *, org_id, github_id, github_username)`** — it tries the immutable github_id first, falls back to the exact-one handle lookup. `github_linkage.github_linkage` (endpoint) and both `_resolve_experiment_owner_user_id` / `_resolve_created_by_user_id` (sweep) call it, so precedence stays identical. Any future lookup dimension MUST be added inside this one function, not duplicated at either call site.
- **M2 refresh must ALSO backfill github_id, still dedicated + fail-open (G4).** The endpoint's refresh-on-miss (`_refresh_org_github_identities`) re-pulls BOTH handle and github_id from Clerk so an un-backfilled-but-correct user can link by `?actor_id`. github_id is set via the shared `auth.provisioning._set_github_id_if_absent` (its `include_deleted` collision pre-check) — never overwrites a differing id, never crashes. It is STILL a dedicated path (NOT `ensure_user_github_identity`/`_refresh_user_github_identity`, which early-return once a handle is set) and STILL `except Exception` fail-open. ONE monkeypatch seam: `_fetch_clerk_identity(clerk_user_id) -> ClerkGithubIdentity` — a single Clerk GET returns both handle and github_id (Codex on G4: don't fetch them separately, that doubles Clerk load per member). The endpoint flushes the refresh writes inside a try/rollback so a collision race / DB error answers from stored state instead of 500ing the read (fail-open extends to the refresh's own writes, not just Clerk outages).
- **Exactly-one:** 0 or 2+ active matches → not-connected / no-owner / None — NEVER an error. Normalization is `@`-strip + `.strip()` + case-insensitive (`func.lower`), org-scoped, `is_active == True`.
- **Org scoping:** never resolve on a bare github_id across orgs — `UniqueConstraint(org_id, github_id)`, lookups always filter `org_id`.
- **Ownership is cosmetic** (the privilege gate is the in-Action push check, not the owner field). `_stamp_experiment_owner` must never be called with None on the exact-one→None path (it no-ops on falsy owner — keep it that way).
- **M2:** the linkage endpoint's Clerk refresh must NOT reuse `ensure_user_github_identity` / `_refresh_user_github_identity` (they early-return when a handle is already set). Use a dedicated, monkeypatchable fetch.
- **M4:** authorize by org + scope; never infer a human identity from an API key (its AuthContext has no user_id).

- **Codex review between every step**: `codex exec -s read-only -` with a *focused* per-slice diff piped on stdin (NOT `codex review --uncommitted` — the working tree carries unrelated WIP that would add noise/cost). Address findings before committing.

- **House style:** terse, minimal comments — but a one-line WHY is warranted for non-obvious correctness/infra (the user dislikes noise, not justified rationale). Reference files with markdown links in prose.
- **github_id source** = Clerk `provider_user_id` (snake_case in the raw REST JSON; a STRING). Column is TEXT. It is an OPTIONAL correctness upgrade for handle renames/recycles — NOT security-critical.
